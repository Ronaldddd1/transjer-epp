AVISOS DE VENCIMIENTO POR WHATSAPP — PASO A PASO
=================================================

Cada mañana el droplet le pregunta a Transjer Gestión qué cuotas de préstamos y servicios
vencen en los próximos 2 días, manda un WhatsApp al número que elijas, y le avisa de vuelta
a la web qué mandó para que ese vencimiento no se repita al día siguiente.

Pregunta el droplet, no al revés, así el servidor de avisos sigue detrás de Tailscale sin
abrir ningún puerto.

El mensaje se ve así:

    *Transjer Gestión* — pagos por vencer
    3 cuota(s) vencen pronto:
    • *15/10/2026* (en 2 días) — SEGURO VEHICULAR BYH716
       Pacífico Seguros · seguro · S/ 620.50
    • *15/10/2026* (en 2 días) — Claro flota
       Claro · servicio · S/ 382.50
    *Total: S/ 1,003.00*


NO HAY QUE TOCAR NINGÚN CÓDIGO
------------------------------

Ni el de Transjer Gestión ni el del servidor de avisos.

El servidor de avisos ya tiene la ruta que hace falta: POST /api/mensaje, la misma que usa
el panel para escribirle a un número suelto. Recibe { telefono, texto }, y por dentro ya
resuelve el JID y comprueba que el número tenga WhatsApp. El script usa esa.

Es un solo archivo para copiar y un archivo de variables para llenar.

------------------------------------------------------------------------------
PASO 2 — Copiar el script al droplet
------------------------------------------------------------------------------

Desde PowerShell, en la carpeta del proyecto:

    scp scripts\aviso-vencimientos.mjs root@avisos-transjer:/home/transjer/transjer-notificaciones/

Y como llega siendo de root, pásalo al usuario que corresponde:

    ssh root@avisos-transjer "chown transjer:transjer /home/transjer/transjer-notificaciones/aviso-vencimientos.mjs"


------------------------------------------------------------------------------
PASO 3 — Buscar el usuario y la clave del panel
------------------------------------------------------------------------------

El panel está protegido con autenticación básica, así que el script necesita esas dos
credenciales para poder usar /api/mensaje. Están en la configuración del servidor:

    ssh root@avisos-transjer
    su - transjer
    grep -rnE "USUARIO_PANEL|CLAVE_PANEL" ~/transjer-notificaciones/.env ~/transjer-notificaciones/src/config.js

Si CLAVE_PANEL sale vacía o no existe, el panel está sin clave — en ese caso deja las dos
variables del paso 4 en blanco, pero conviene ponerle una: hoy cualquiera que llegue a ese
puerto puede mandar WhatsApp desde el número de la empresa.


------------------------------------------------------------------------------
PASO 4 — El archivo de variables
------------------------------------------------------------------------------

Como usuario transjer, en la carpeta del servidor:

    nano ~/transjer-notificaciones/.env.avisos

Con esto adentro:

    TRANSJER_URL=https://transjer-epp.vercel.app
    AVISOS_SECRET=0sNLvEwfhnWgHyNPQO56UdgnH8dTlW5YVWA916w7+1I=
    AVISOS_DESTINO=51XXXXXXXXX
    AVISOS_PANEL=http://127.0.0.1:3000/api/mensaje
    AVISOS_PANEL_USUARIO=...el USUARIO_PANEL del paso 3...
    AVISOS_PANEL_CLAVE=...la CLAVE_PANEL del paso 3...
    AVISOS_DIAS=2

AVISOS_DESTINO es el número que recibe los avisos, con código de país y sin el +.

Lleva dos claves, así que que no la pueda leer nadie más:

    chmod 600 ~/transjer-notificaciones/.env.avisos

El script lee este archivo él mismo. No hay que cargarlo antes con
"set -a; . ./.env.avisos": por ahí, una clave con un espacio o con caracteres como $ o `
se parte, el shell se queda con el primer trozo e intenta ejecutar el resto, y la variable
llega a medias. El envío falla con un 401 que no se explica mirando el archivo, porque ahí
la clave está bien escrita. Leyéndolo desde el script, el valor llega entero sea cual sea.


------------------------------------------------------------------------------
PASO 5 — Probar sin mandar nada
------------------------------------------------------------------------------

    cd ~/transjer-notificaciones
    node aviso-vencimientos.mjs --simular

Imprime el mensaje que mandaría, sin mandarlo y sin marcar nada.

Si dice "Nada vence en los próximos 2 día(s)", funcionó: es que de verdad no hay nada
venciendo. Para verlo igual:

    AVISOS_DIAS=30 node aviso-vencimientos.mjs --simular


------------------------------------------------------------------------------
PASO 6 — Probar de verdad
------------------------------------------------------------------------------

    node aviso-vencimientos.mjs

Tiene que llegarte el WhatsApp, y en pantalla:

    N cuota(s) por avisar.
    Mensaje enviado a 51XXXXXXXXX.
    N cuota(s) quedaron marcadas como avisadas.

Córrelo una segunda vez seguida: tiene que decir "Nada vence…". Eso confirma que no va a
repetir el mismo aviso todos los días hasta que pagues, que es lo que hace que la gente
deje de leer los avisos automáticos.

Si el envío falla no marca nada y sale con error, así que el aviso se reintenta mañana en
vez de perderse en silencio.


------------------------------------------------------------------------------
PASO 7 — Programarlo
------------------------------------------------------------------------------

Como usuario transjer, no como root:

    crontab -e

Y al final, de lunes a sábado a las 8 de la mañana, todo en una sola línea:

    0 8 * * 1-6 cd /home/transjer/transjer-notificaciones && /usr/bin/node aviso-vencimientos.mjs >> /home/transjer/avisos-vencimientos.log 2>&1

Revisa que el droplet esté en hora de Lima:

    timedatectl
    # si no lo está:  sudo timedatectl set-timezone America/Lima

A los días, para ver que viene corriendo:

    tail -20 /home/transjer/avisos-vencimientos.log

QUÉ SIGNIFICA CADA ERROR
------------------------------------------------------------------------------

"No se pudo conectar con https://transjer-epp.vercel.app/... (ENOTFOUND)"
    La dirección está mal escrita, o el droplet se quedó sin salida a internet.

"/api/avisos/vencimientos respondió 401"
    La AVISOS_SECRET del droplet y la de Vercel no son la misma.

"El panel de avisos rechazó el acceso (401)"
    AVISOS_PANEL_USUARIO o AVISOS_PANEL_CLAVE no coinciden con las del servidor de avisos.
    Vuelve al paso 3.

"No se pudo conectar con http://127.0.0.1:3000/api/mensaje (ECONNREFUSED)"
    El servidor de avisos está caído:  su - transjer && pm2 list

"El panel de avisos respondió 400: Celular inválido"
    AVISOS_DESTINO está mal escrito.

"El panel de avisos respondió 400: WhatsApp no está conectado"
    Baileys perdió la sesión. Entra al panel por Tailscale y vuelve a escanear el QR.
    El aviso no se marcó, así que se reintenta.

Llegó el aviso pero con cuotas de menos
    Las ya avisadas no se repiten. Para forzar que vuelvan a salir, en la base:
        update obligation_installments set reminder_sent_at = null where id in (...);

Cambiar el número o los días de anticipación
    Edita .env.avisos. No hace falta tocar código ni volver a desplegar nada.

Que avise a varios números
    Hoy manda a uno solo. Avísame y lo cambio.


------------------------------------------------------------------------------
UN DETALLE DE TU SERVER.JS, APARTE DE TODO ESTO
------------------------------------------------------------------------------

En la comprobación de la clave del panel:

    const ok = recibido.length === esperado.length &&
      crypto.timingSafeEqual(Buffer.from(recibido), Buffer.from(esperado));

`recibido.length` cuenta caracteres y `Buffer.from(recibido)` cuenta bytes, que no es lo
mismo cuando hay caracteres fuera del ASCII. Una cabecera con el mismo número de
caracteres pero más bytes pasa el primer filtro y hace que timingSafeEqual lance una
excepción: el servidor responde 500 en vez de 401.

No deja entrar a nadie —no es un agujero de seguridad—, pero un pedido mal formado tumba
el manejador. Se arregla comparando bytes con bytes:

    const esperadoBuf = Buffer.from(esperado);
    app.use((req, res, next) => {
      const recibido = Buffer.from(req.headers.authorization || '');
      const ok = recibido.length === esperadoBuf.length &&
        crypto.timingSafeEqual(recibido, esperadoBuf);
      if (ok) return next();
      res.set('WWW-Authenticate', 'Basic realm="TransJer"').status(401).send('Acceso restringido');
    });

Lo probé contra una copia de tu middleware antes de decírtelo. Tú decides si vale la pena
tocarlo: estando detrás de Tailscale, el impacto es bajo.
